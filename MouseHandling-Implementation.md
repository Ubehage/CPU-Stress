`Button`, `CheckBox`, and `CPUView` now use the shared mouse manager. All three controls have removed their local capture ownership and cursor polling. CPUView no longer emits `Click(0)` for empty space. The original baseline analysis is in [MouseHandling.md](MouseHandling.md).

The exportable component consists of [modMouse.bas](modMouse.bas), [IMouseSink.cls](IMouseSink.cls), and [CMouseTarget.cls](CMouseTarget.cls). The third file is an internal state record: a dispatch can retain it while a callback unregisters its window, without using object-pointer reconstruction or reusing a removed record. Import all three files into a VB6 project. They require the VB6 runtime and the Windows User32, Kernel32, and Common Controls APIs; they have no CPU-Stress dependencies or additional OCX requirements. Named subclass APIs were verified on this development machine; deployment compatibility with older Windows installations is not yet established.

Implement `IMouseSink` in a class or control, register its window, and store the nonzero token. Registration rejects duplicate windows, invalid handles, other threads, and IDE execution. Call `MouseLastError()` for native registration or recipient error details. `HitTest` receives signed client pixels and returns a positive region ID, or zero for empty space. The manager checks visible client bounds, ancestor enablement, foreground ownership, and occlusion before invoking the hit test. Right/bottom edges are exclusive.

`OnMouse` receives Enter, Leave, Move, Down, Up, Click, and Cancel. Crossing a region boundary reports Leave(old), Enter(new), then Move. Only left presses arm a click; they retain the origin region while moving outside. Capture is acquired only if the target does not already own it: redundantly acquiring capture can trigger capture-change processing in a native control and cancel its press. On release, capture is released before Up and a possible Click. VB6's default MouseUp processing is allowed to release capture without falsely cancelling the gesture. Capture theft, cancellation, changed registration/state, or a different release region suppresses Click. Notifications are synchronous; a recipient may disable, unregister, hide, or destroy its target. Do not use `DoEvents` as a normal part of notification handling.

The manager tracks actual pointer region separately from a retained press. Button and CheckBox preserve their pressed appearance while dragging outside. Controls retain their drawing, colors, captions, value changes, and public Click events; Button also retains keyboard activation. CheckBox still toggles before notifying its Click recipient and preserves programmatic Value/ChangedByCode behavior. Native MouseMove/Down/Up handling is centralized; the controls' remaining VB mouse handlers provide the IDE fallback only.

CPUView converts the manager's client pixels to its existing twip-based drawing coordinates and returns a positive core index, or zero for headings and gaps. Pressed and hovered core indices remain independent. A release on another core or empty space cannot complete a click, and the main form also rejects out-of-range CPU indices before accessing shared memory. Region transitions and cancellation repaint affected cores completely, including clearing old highlights. Full refresh measures headings before rebuilding geometry and repaints current hover/pressed state. All three sizing modes refresh drawing and hit testing together. CPU load collection, timer behavior, busy/hibernation state, and public indexed Click delivery remain local to CPUView.

For standard modules, [ModuleMouseSink.cls](tests/ModuleMouseSink.cls) is a minimal adapter example. It implements the typed contract and forwards notifications into a `.bas` routine. Replace the example destination with the consuming module and provide its hit test. Ordinary object references keep registered recipients alive; callers must explicitly unregister instead of depending on class termination.

Lifecycle responsibilities:

- Register runtime windows after they exist. Do not register design-time controls.
- Forward custom Enabled changes through `MouseSetEnabled`; VB properties need not correspond to native window enablement.
- Unregister before disposing a recipient. Unregister and shutdown are silent and idempotent; window destruction also detaches registrations.
- Use `MouseCancel`/`MouseCancelAll` for cancellation and owner deactivation. Cancel clears pending interaction before notifying; it may also notify an idle recipient so the control can clear keyboard state.
- Use `MouseRefresh`/`MouseRefreshAll` after layout, activation, or owner movement. These helpers reevaluate the current cursor position without capturing it.
- Call `MouseShutdown` during application shutdown. The All helpers operate on every registration on this UI thread; a larger multi-form host may prefer forwarding individual tokens.

CPU-Stress forwards form activation, deactivation, resizing, and shutdown. The existing hibernation hook additionally refreshes mouse geometry after the main window moves, so no second parent subclass is introduced. Its original power notification path is retained. All three controls detach on Hide and register again on Show, clear local interaction state on teardown, and avoid touching themselves after raising Click because a recipient can unload them. A destroyed child detaches through `WM_NCDESTROY` even if normal teardown was missed. Exceptions from hit tests or notifications are contained, recorded, and detach the failed recipient.

The compiled application uses native subclassing. In the VB6 IDE, `MouseNativeAvailable()` returns False and registration is disabled to avoid callbacks surviving IDE Stop/Reset. All three controls support conventional mouse clicking there, and Button retains Space/Return activation. Passive hover highlighting is intentionally unavailable in the IDE. CPUView's fallback also requires a positive matching press/release index. The native tracking tests must run as a compiled executable; the IDE fallback has not been manually exercised.

Build from the workspace root:

```powershell
rtk proxy powershell -NoProfile -File tools\Build-VB6.ps1
rtk proxy powershell -NoProfile -File tools\Test-Mouse.ps1
```

The app build goes to `build\app`; it does not replace the existing root executable. Build logs use unique timestamps. The installed VB6 compiler needs registry access that the restricted execution sandbox does not provide, so compilation here required execution outside that sandbox. Keep exported VB6 files in their normal ANSI/CRLF format; a newly written form with LF-only lines failed to load in this compiler.

The test executable has no CPU worker/startup code. It compiles the real three controls and the real timer class, with a deterministic four-core CPU inventory from [modCPUFixture.bas](tests/modCPUFixture.bas); CPU live updates remain off during mouse tests. It briefly shows its own forms, uses native message-driven interactions and real Windows capture, samples control pixels after painting, and restores the previous cursor position. Run on an unlocked desktop without competing input. An inability to make the test form foreground aborts the interaction tests instead of weakening that precondition. If Windows denies background activation, launch `build\tests\MouseTests.exe /manual` and click OK in its start dialog. This harness does not replace physical-input testing, actual CPU/PDH monitoring validation, real suspend/resume testing, or checks on other DPI/Windows configurations.

Occlusion follows Windows input hit testing, including its deliberate pass-through behavior for static text controls. The occlusion and destruction fixtures use native BUTTON windows and assert that those fixtures receive input before checking the manager's behavior.
