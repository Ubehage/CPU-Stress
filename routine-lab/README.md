# Routine Lab

Routine Lab is a small VB6 workbench for loading hexadecimal machine code, running a bounded experiment, and inspecting its return value, scratch data, and execution time. It includes a direct WOW64 mode: **64-bit instructions execute inside a 32-bit worker process**, then return to VB6. The production CPU Stress application and its stress loop are separate from this workbench.

## Build and open

From the project root:

```powershell
rtk proxy powershell -NoProfile -File tools\Build-RoutineLab.ps1
rtk proxy powershell -NoProfile -File tools\Test-RoutineLab.ps1 -SkipBuild
```

The build uses the VB6 compiler described in [VB6.md](../VB6.md), plus NASM and an AMD64 MinGW GCC toolchain. Its default native tools directory is `C:\Users\Ubehage\Documents\WinLibs\mingw64\bin`; override it with `-NativeTools` on the build script. NASM assembles the samples and `native/wow64-gate.asm`; generated bytes are build outputs, not manually maintained instruction strings.

Open `build\routine-lab\RoutineLab.exe` without arguments to show the workbench. Select a sample, choose execution mode, set iterations and timeout, and click **Run routine**. The hex editor accepts whitespace-separated two-digit bytes and semicolon line comments. **Stop** terminates the current worker. Each GUI run saves its input and report in a unique directory under `build\routine-lab\runs`.

Compile before executing routines. Native execution is intentionally disabled inside the VB6 IDE.

## Execution modes

| Mode | Where instructions run | Routine input |
| --- | --- | --- |
| `x86` | Disposable 32-bit copy of RoutineLab | 32-bit machine code |
| `wow64` | That 32-bit process temporarily executes x64 code through the local bridge | 64-bit machine code |
| `x64` | Separate native `RoutineWorker64.exe` | 64-bit machine code, for comparison |

Direct WOW64 mode is experimental and targets x86 programs under native AMD64 Windows. It relies on Windows code selectors `0x23` and `0x33`; it is not intended for 32-bit Windows or ARM64 emulation. It does not load a 64-bit DLL through VB6, and it does not expose a general interface for calling 64-bit Windows APIs. Keep routines local and self-contained. No system mitigation settings need to be disabled by this project; an incompatible environment should report failure rather than be reconfigured.

The existing AVX/YMM instructions are not inherently 64-bit-process instructions. The direct proof instead uses 64-bit arithmetic, extended registers, and a result that exceeds 32 bits. See [StressLoop-Analysis.md](../StressLoop-Analysis.md) for the instruction audit and source references.

## Routine contracts

For `x86`, entry stack arguments are:

| Location at routine entry | Value |
| --- | --- |
| `[esp+4]` | Reserved, zero |
| `[esp+8]` | Writable scratch pointer |
| `[esp+12]` | Positive iteration count |
| `[esp+16]` | Scratch size, 4096 bytes |

Return the result in EAX using `ret 16`. Preserve EBX, ESI, EDI and EBP, restore ESP, and leave the direction flag clear. Adding a frame-pointer prologue changes argument offsets; these offsets describe the untouched entry stack.

For both x64 modes, use the Windows x64 calling convention:

| Register | Value |
| --- | --- |
| RCX | Reserved, zero |
| RDX | Writable scratch pointer |
| R8 | Positive iteration count |
| R9 | Usable scratch size: **4080 for WOW64**, **4096 for native x64** |
| RAX on return | Full 64-bit result |

Return with ordinary `ret`. Preserve nonvolatile registers, including the low 128 bits of XMM6-XMM15, and restore the stack exactly. The bridge reserves the final 16 bytes of its allocation for return/context reporting; do not write beyond R9 bytes. A routine using AVX should perform `vzeroupper` before returning. The supplied samples show the relevant register preservation. Start with leaf routines; arbitrary external calls, callbacks, exceptions, and stack unwinding across the WOW64 boundary are outside this workbench's contract.

Iterations are an argument to the routine, not a loop imposed by the workbench. A routine can ignore the count. The controller's timeout remains active independently and terminates a worker that does not return.

Code memory is allocated separately, filled while writable, changed to executable/readable, and followed by an instruction-cache flush. The worker releases its allocations after a normal return. Every run starts a fresh process with zeroed scratch memory.

## Samples and output

| Sample | Requirement | Expected result |
| --- | --- | --- |
| `return42-x86` | `base` | EAX = `0000002A` |
| `proof64-x64` | `base` | RAX = `1122334555667788`; first eight scratch bytes = `8877665545332211` |
| `sse2-x86` | `sse2` | Four independent packed-single chains, iteration count returned |
| `sse2-x64` | `sse2` | Same arithmetic under either x64 mode |
| `fma-x64` | `fma` | Eight independent 256-bit FMA chains, iteration count returned |

The arithmetic samples use the bounded recurrence `x = x * (1 - 2^-24) + 2^-23`, starting at 0.5 in every lane. Values evolve with the iteration count while remaining finite. SSE2 rounds the multiplication and addition separately; FMA rounds their combined result once. Tests compare one and 31 iterations against independent scalar reference calculations with those rounding rules. SSE2 samples execute 32 floating-point operations per loop iteration; the FMA sample executes 128. This makes them controlled comparison workloads, not established maximum-power kernels.

The requirement selector gates execution on CPU/OS support. AVX requires the hardware flags, OSXSAVE, and enabled XMM/YMM state; FMA additionally requires the FMA flag. The selector does not inspect arbitrary machine code to infer which instructions it contains. Choose the requirement matching your routine.

Reports are `key=value` text:

- `status`: `ok`, `error`, `unsupported`, `exception`, `crash`, `timeout`, or `cancelled`.
- `architecture`: `x86`, `wow64-x64`, or `x64` for workers.
- `iterations`: the requested count.
- `elapsed_ms`: time around the routine call; excludes process startup. WOW64 timing includes its transition bridge.
- `return_hex`: EAX or the complete RAX value, most significant digit first.
- `scratch_hex`: the first 16 scratch bytes in memory order, so integer stores appear little-endian.
- `code_segment`: WOW64 bridge's observed code selector, expected `0033` on success.
- `error`: diagnostic text when available. Native comparison reports also include AVX/FMA feature flags.

An exception may terminate a worker before it can write diagnostics; the controller then reports a crash. The controller owns its worker through a kill-on-close Windows job so closing or stopping the controller does not leave the worker running. Process fault isolation is **not a security sandbox**: run only local routines you trust, since machine code has the worker's ordinary user permissions.

## Command-line testing

```text
RoutineLab.exe /run <x86|wow64|x64> <hex-path> <iterations> <timeout-ms> <report-path> <base|sse2|avx|fma>
```

Quote file paths containing spaces. Iterations and timeout must be positive decimal integers no larger than 2147483647. The report's parent directory must already exist. Exit code zero means `status=ok`; other outcomes produce a nonzero exit code. Input and report paths must differ.

For example, from the project root:

```powershell
rtk proxy build\routine-lab\RoutineLab.exe /run wow64 build\routine-lab\routines\proof64-x64.hex 7 3000 build\routine-lab\proof-result.txt base
```

`tools/Test-RoutineLab.ps1` verifies executable architectures, the full 64-bit proof in both x64 modes, scratch-size contracts, x64 stack alignment, evolving arithmetic against a scalar reference, feature gating, malformed input, zero counts, deliberate invalid instructions, timeouts, and successful runs after faults. Tests use small counts and a separate 15-second controller deadline. Unsupported FMA is recorded as a skip; a failed WOW64 proof is a failure. Reports remain under `build\routine-lab\test-runs` for inspection.

The 2026-11-03 local run passed **310 checks, with no feature skips**. It observed `0033` during the direct WOW64 execution and the expected complete 64-bit result. Arithmetic at one and 31 iterations matched the independent reference, with different outputs for the two counts. Deliberate faults and endless loops were contained in all three modes, followed by successful recovery runs. This result establishes compatibility on this tested machine, not every Windows configuration.

Timing these tiny checks establishes functionality, not thermal performance. Longer comparisons should record throughput together with package power, temperature, clock rate and throttling before choosing a replacement production stress kernel.
